# Load and PV Analysis

A Python data pipeline for analyzing interval electricity-load data, classifying consumption under a PEA time-of-use tariff, estimating PV self-consumption and curtailment, recommending a battery size, and searching for an optimal PV capacity.

The main workflow is:

```text
raw load data
    -> 1_data_cleansing_aggregate.py
    -> 2_exploratory_data_analysis.py
    -> 3_load_clascify.py
    -> 4_load_pv_batt.py
    -> temporary/ and result_<year>/
```

The project is currently configured for the 2022 IWRM dataset. The scripts are mostly year-agnostic, but several input paths and calendar assumptions are hardcoded and must be updated for other datasets.

## Requirements

- Python 3.10 (the current environment was verified with Python 3.10.11)
- Windows PowerShell for the commands below
- No network access is required by the main pipeline: step 4 reads a local solar profile

Python packages are pinned in `requirements.txt`. The global interpreter in this environment does not have the dependencies installed; use the project `.venv`.

## Setup

Run from the repository root:

```powershell
py -3.10 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
```

Optional for non-interactive runs:

```powershell
$env:MPLBACKEND = "Agg"
```

`MPLBACKEND=Agg` prevents plots from opening interactively. Some scripts call `plt.show()`, but with the Agg backend the plots are effectively non-interactive.

## Quick Start

Run the main pipeline in order:

```powershell
python 1_data_cleansing_aggregate.py
python 2_exploratory_data_analysis.py
python 3_load_clascify.py
python 4_load_pv_batt.py
```

Step 4 reads `solar_1kW_<year>.csv` directly from the repository root, where `<year>` is taken from the first load timestamp. The file is required; there is no NASA POWER/clear-sky fallback in step 4 (a missing file raises `FileNotFoundError`). `solar_profile.py` remains available as a standalone builder.

The `0_*.py` scripts are optional preparation utilities and are not required for the main `1 -> 4` workflow.

## Script Reference

### `0_conbine_data.py`

Optional Tkinter utility for combining monthly AMR Excel files into one CSV.

- Selects source and output directories through a GUI.
- Unmerges cells before reading.
- Handles PEA-style dates, Buddhist-era years, and `24:00`.
- Sums `RATE A`, `RATE B`, and `RATE C` columns.
- Writes `combined_data.csv` and `combined_data_homer.csv`.

Format settings are hardcoded near the top of the script. Adjust `skiprows_count`, rate-column names, timestamp format, and column indexes for other AMR formats.

### `0_convert_time_format.py`

Converts:

```text
source/created_load_pattern.csv
```

to:

```text
source/created_load_pattern_edit.csv
```

The output timestamp format is `%d/%m/%Y %H.%M`.

### `0_create_load_pattern.py`

Builds a synthetic 15-minute load profile from annual on-peak, off-peak, and holiday energy totals.

- The current year and demand values are hardcoded for 2023.
- Uses PEA weekday/weekend/holiday masks.
- Writes `source/created_load_pattern.csv` and `source/created_load_pattern_edit.csv`.

### `0_excel_split_sheet.py`

Splits every sheet in an Excel workbook into a separate `.xlsx` file. The input path is hardcoded and must be edited before use.

### `load profile/flat_load_profile_template.py`

Standalone helper for generating simple 15-minute flat load-profile templates. It is not part of the main pipeline.

### `1_data_cleansing_aggregate.py`

Loads and cleans the raw interval load data.

- Input path is hardcoded as `source/iwrm/EnergyDayChartAll2022_edit.csv`.
- Accepts several timestamp formats, including `%d/%m/%Y %H.%M`.
- Renames `Date`/`Load` to `timestamp`/`load`.
- Interpolates missing values.
- Resamples interval data to hourly averages.
- Adds `day_of_week` and `month`.
- Creates `result_<year>/` from the first timestamp's year.

Main outputs:

- `temporary/dummy.csv`: cleaned interval data
- `temporary/prepared_electric_load_data.csv`: hourly load data
- `temporary/daily_peak_load_data.csv`: daily maximum load
- `temporary/montly_peak_load_data.csv`: month-end maximum load
- `result_<year>/peak_day.png`: maximum/minimum day and yearly average profile

Note: the filename `montly_peak_load_data.csv` is intentionally documented with the spelling used by the code.

### `2_exploratory_data_analysis.py`

Reads the hourly prepared data and adds lag features:

- `load_lag1`: previous hour's load
- `load_lag2`: load two hours earlier

Outputs:

- `temporary/analyse_electric_load_data.csv`
- `result_<year>/anual_load.png`
- `result_<year>/Seasonal_comparison.png`
- `result_<year>/Seasonal.png`
- `result_<year>/Seasonal_specific_1.png` through `Seasonal_specific_5.png`
- `result_<year>/LoadVariation.png`

The correlation heatmap and the 30-day rolling-mean chart are displayed but not saved.

### `3_load_clascify.py`

Classifies load into tariff groups and calculates base electricity costs.

Current tariff assumptions:

- On-peak and off-peak energy: `5.5 THB/kWh`
- Demand charge: `74.14 THB/kW`
- Service charge: `312.24 THB/month`
- Excludes FT and VAT

Time rules:

- On-peak: weekdays, 09:00-21:59
- Off-peak: other weekday hours
- Holiday: weekends plus the hardcoded PEA holiday dates

Main outputs:

- `result_<year>/Energy consumption_result.txt`
- `temporary/anual_electricity_base_price.json`
- `temporary/weekdays_data.csv`
- `temporary/weekends_data.csv`
- `result_<year>/average_weekday_weekend.png`
- `result_<year>/average_load_every_day.png`
- `result_<year>/load_duration_curve_all_days.png`
- `result_<year>/load_duration_curve_all_months.png`
- `result_<year>/load_duration_curve_weekdays_weekends.png`
- `result_<year>/load_distribution.png`

`temporary/load_without_pv.csv` is produced by a test section and is not consumed by step 4.

The holiday list currently covers 2021-2024. Update it when processing other years.

### `4_load_pv_batt.py`

Combines the hourly load data with a local PV profile and evaluates PV self-consumption, curtailment, a battery-size recommendation, and an optimal PV size.

Current configuration:

- Solar input: `solar_1kW_<year>.csv` from the repository root (fixed-tilt profile)
- Tracking: disabled by default; switch the commented line to `solar_1kW_<year>_tracking.csv` to use it
- Preset capacities: `1,000` and `4,000 kWp`
- PVSyst reference yields: `1,452` and `1,600 kWh/kWp/year`
- Solar normalization reference: `1,402.8119 kWh/kWp/year`
- PV adjustment factors: `1,452 / 1,402.8119` and `1,600 / 1,402.8119`
- Optimal-capacity search target: `20%` curtailment
- Search bounds: `0` to `100,000 kW`
- Search tolerance: `0.1%`

The latitude/longitude and `PVGIS_TMY` import are retained, but the solar model is no longer called from this script; the profile is read directly from the CSV. `temporary/` must already exist (steps 1-3 create it), because step 4 no longer creates it.

For a capacity in `PV_Install_Capacity`, the matching adjustment factor is used. For any other capacity, the current code sets the gain to the mean PVSyst yield (`1,526`) instead of the mean adjustment factor (`~1.0878`). This is a known bug: PV output for non-preset capacities is inflated by roughly the normalization factor, so the optimizer collapses toward `0 kW`. Preset `1,000` and `4,000 kWp` results are unaffected. See Known Limitations.

Per-capacity calculations include:

- `pv_produce`
- `pv_serve_load`
- `pv_curtailed`
- `load_existing`
- Capacity factor, using an annual denominator of `8,760` hours
- On-peak, off-peak, and holiday PV-served energy
- CO2 reduction using `0.4857 kg-CO2/kWh`
- Battery sizing heuristic based on the 60th percentile of daily curtailed energy

Main outputs:

- `solar_pattern.csv` (repository root, not `temporary/`)
- `temporary/pv_data_for_train_model.csv`
- `temporary/param_for_economic.json`
- `temporary/load_pv_profile.csv`
- `result_<year>/load_pv_batt_result_1000.txt`
- `result_<year>/load_pv_batt_result_4000.txt`
- Monthly PV/load plots for each preset capacity
- Hourly load/PV profile plots for each preset capacity
- Daily curtailment percentile plots for each preset capacity
- `result_<year>/average_load_pv_profile_<capacity>kWp.csv` for every capacity evaluated, including all binary-search iterations (typically ~18 files: `0`, `1`, `2`, `3`, `6`, ... `50,000 kWp`)

`temporary/load_pv_profile.csv` is overwritten on every internal evaluation. The final file therefore corresponds to the last capacity evaluated by the optimizer.

### `solar_profile.py`

Standalone PV profile builder. Step 4 no longer imports or calls it; it is kept for regenerating local profiles.

Builds or loads a normalized PV profile. Resolution order:

1. Existing `solar_1kW_<year>.csv` when `force_fallback=False`
2. NASA POWER profile from `solar_cache/`, if present
3. Fresh NASA POWER request plus a pvlib fixed-tilt model
4. Clear-sky profile from `solar_cache/`, if present
5. Fresh clear-sky pvlib profile

If a tracking profile is requested, an existing `solar_1kW_<year>_tracking.csv` must be supplied. The fallback model currently supports fixed-tilt profiles only.

Model assumptions:

- Timezone: `Asia/Bangkok`
- Albedo: `0.2`
- Irradiance transposition: Hay-Davies
- Cell temperature: SAPM
- DC model: PVWatts
- AC model: PVWatts inverter with `96%` nominal efficiency
- Default normalization target: `1,402.8119 kWh/kWp/year`

Solar files must contain `timestamp` and `pv` columns, with timestamps in `%d/%m/%Y %H:%M` format.

### `PVGIS_TMY.py`

Legacy helper that requests a TMY file from PVGIS and writes `tmy_data.csv`. It returns total GHI and an estimated annual PV yield. Step 4 imports this module but does not call it in the current workflow.

## Inputs

### Load data

The current input is:

```text
source/iwrm/EnergyDayChartAll2022_edit.csv
```

It contains `Date` and `Load` columns. Step 1 accepts several timestamp formats and resamples the interval data to hourly averages.

### Solar profiles

The root-level files are:

```text
solar_1kW_<year>.csv
solar_1kW_<year>_tracking.csv
```

Each file contains:

```text
timestamp,pv
```

The `pv` column represents hourly PV output per installed kWp. Step 4 requires the file matching the load year; for the 2022 dataset this is `solar_1kW_2022.csv`. There is no fallback if the file is missing.

Profiles such as `temporary/solar_compare/nasa_2022_normalized.csv` are reference profiles at 1 kWp, not at a specific installed capacity. Their annual yield is normalized to `1,402.8119 kWh/kWp/year`; installed capacity is applied later when PV production is calculated. For example, `1,000` and `4,000 kWp` are multipliers used in the PV analysis, not properties of the normalized profile file.

### Legacy TMY data

`tmy_data.csv` is the PVGIS TMY output. It is not required for the current default run.

### Load-profile templates

`load profile/` contains flat 15-minute templates and `flat_load_profile_template.py` for generating new templates.

## Solar Profile Comparison: Local vs NASA POWER 2022

A standalone comparison was run to check whether the local PV profile is interchangeable with an online NASA POWER profile for 2022. The experiment did not modify `result_2022/` or the main pipeline.

Method:

- Fetch NASA POWER 2022 at the project coordinates.
- Build a PV profile with the same PVWatts model and assumptions as `solar_profile.py`.
- Normalize the NASA profile to the local annual yield of `1,402.8119 kWh/kWp/year`.
- Compare profile shape and PV metrics against `solar_1kW_2022.csv`.

The NASA profile is a 1 kWp reference profile. It is not calculated at `1,000` or `4,000 kWp`; those capacities are applied only in the PV metrics calculation.

Annual yield before normalization:

| Profile | Annual yield |
| --- | --- |
| Local `solar_1kW_2022.csv` | `1,402.8119 kWh/kWp/year` |
| NASA POWER 2022 raw | `1,523.1679 kWh/kWp/year` |
| NASA POWER 2022 normalized | `1,402.8119 kWh/kWp/year` |

Profile shape metrics for NASA normalized vs local:

| Metric | Value |
| --- | --- |
| All-hours hourly correlation | `0.8956` |
| Daytime hourly correlation | `0.7621` |
| Daytime hourly correlation (> `0.1 kW/kWp`) | `0.6056` |
| Daily correlation | `0.0619` |
| Rolling 30-day daily correlation | `0.5617` |
| Monthly correlation | `0.5510` |
| Maximum monthly share difference | `1.66 pp` |
| Peak output | local `0.7513`, NASA `0.8841 kW/kWp` |
| Mean peak-hour shift | `0 h` |

PV metrics:

| Case | Local served | NASA served | Served change | Local curtailment | NASA curtailment |
| --- | --- | --- | --- | --- | --- |
| `1,000 kWp` | `596,747.3 kWh` | `587,657.0 kWh` | `-1.52%` | `58.90%` | `59.53%` |
| `4,000 kWp` | `810,078.1 kWh` | `855,943.5 kWh` | `+5.66%` | `87.34%` | `86.63%` |
| Optimal (`20%` target) | `268,207.5 kWh` | `215,815.5 kWh` | `-19.53%` | `20.01%` | `20.10%` |

The optimal capacities are `219.73 kWp` for the local profile and `177.00 kWp` for the normalized NASA profile, a change of `-19.44%`.

Interpretation:

- Annual and monthly energy are similar, but the daily pattern is not: daily correlation is only `0.0619`.
- All-hours correlation (`0.8956`) is inflated by matching nighttime zeros; daytime correlation (`0.7621`) is the more meaningful profile metric.
- The optimal PV capacity changes from `219.73` to `177.00 kWp` (`-19.44%`), so the profiles are not interchangeable for sizing.
- The comparison is classified as **different** using the project thresholds (close: daytime correlation >= `0.95`, monthly share difference <= `5 pp`, optimal capacity difference <= `5%`).
- The local `solar_1kW_2022.csv` and `solar_1kW_2023.csv` files have identical `pv` arrays. The local profile therefore behaves like a reference/typical-year profile rather than independent observed-2022 data.

Experiment artifacts are written to the ignored directory `temporary/solar_compare/` and are not committed.

## Known Limitations

- `1_data_cleansing_aggregate.py` hardcodes the input path as `source/iwrm/EnergyDayChartAll2022_edit.csv`.
- The result folder is named from the first timestamp's year. Processing another year still requires the correct input path.
- The PEA holiday list in step 3 and step 4 covers 2021-2024 only. Add new dates for other years.
- Step 4 reports a fixed set of preset capacities: `1,000` and `4,000 kWp`.
- PV correction factors are calibrated from two capacity points. For other capacities the code currently uses the mean PVSyst yield (`1,526`) instead of the mean adjustment factor (`~1.0878`). This inflates PV output by roughly `1,402.8x`, so the optimal-capacity search collapses toward `0 kW`. Do not trust the optimal capacity until this is fixed; the `1,000`/`4,000 kWp` results are correct.
- Step 4 reads `solar_1kW_<year>.csv` directly and has no fallback. `solar_profile.py` (NASA POWER/clear-sky, fixed-tilt only) is standalone and must be run separately to create profiles.
- `solar_1kW_2022.csv` and `solar_1kW_2023.csv` have identical `pv` arrays; the local profile is a reference/typical-year profile, not independent observed-2022 data.
- The NASA POWER 2022 comparison shows similar annual/monthly yield but weak daily correlation (`0.0619`) and a `-19.44%` difference in optimal capacity, so NASA 2022 is not a drop-in replacement for the local profile at daily resolution.
- The battery recommendation is a heuristic based on the 60th percentile of daily curtailed energy. The battery economic/savings block was removed from step 4.
- Step 4 writes `average_load_pv_profile_<capacity>kWp.csv` for every capacity it evaluates, so a run leaves about 18 files in `result_<year>/`, including binary-search iterations.
- `solar_pattern.csv` is written to the repository root and is not ignored by `.gitignore`.
- `result_2022/` is tracked in Git even though it contains generated outputs; avoid committing incidental changes.
- The `Total Base Price` printed by step 4 is computed from PV-served energy and demand values. It is an indicative PV value calculation, not the full remaining electricity bill after PV installation.
- Capacity factor calculations assume `8,760` hours in a year; leap years are not adjusted to `8,784`.
- Correlation and rolling-mean plots in step 2 are shown but not saved.
- `temporary/load_without_pv.csv` is a test artifact and is not part of the downstream workflow.
- `PVGIS_TMY.py` is legacy and writes `tmy_data.csv` when called.
- There is no automated test suite. Verify changes by running `py_compile` and the full pipeline.
- The scripts use Windows-style paths and should be run from the repository root.
